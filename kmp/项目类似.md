有，类似架构在 Android Root/KPM 圈子里很常见。最接近你这个“驱动 + Shell 脚本 + WebUI/启动服务”的公开方案是：

| 项目                                                                        | 相似点                                                                                                                               |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| [qinghemuyu/hidhide-module](https://github.com/qinghemuyu/hidhide-module) | 最接近完整工程：`kpm/` 驱动源码、`load.sh` 加载器、`service.sh` 开机服务、`module.prop`、`webroot/` KernelSU WebUI、`pack.sh` 打包 ZIP。还同时支持 KPM 和传统 `.ko`。 |
| [qinghemuyu/memagent-kpm](https://github.com/qinghemuyu/memagent-kpm)     | KPM 驱动配合 PC/ADB 控制端；有 `patch_boot.sh`，可把 KPM 写入 boot/init_boot 后开机加载。和“内核能力 + 脚本安装/加载”的关系很直接。                                     |
| [kelexine/kpm-rootstealth](https://github.com/kelexine/kpm-rootstealth)   | 典型单 KPM 项目：编译 `.kpm`，复制到 `/data/adb/kpmodules/`，通过 APatch Manager 的 KPM 控制面加载和传命令。                                                |
| [bmax121/KernelPatch](https://github.com/bmax121/KernelPatch)             | KPM 格式、加载器和内核 hook 的底层参考实现。你的 `page_dog.kpm` 如果属于 KernelPatch 体系，应以它的模块 API 和加载链作标准。                                              |
| [KPatch-Next-Module](https://github.com/SukiSU-Ultra/KPatch-Next-Module)  | KPM 运行时加载、KernelSU/Magisk 封装、WebUI 和 boot 补丁的工程参考。你当前目录已下载了一份源码。                                                                  |

你现在项目的常见重构目标结构应接近：

```
module/
  module.prop
  customize.sh
  service.sh
  uninstall.sh
  webroot/
  bin/
    controller      # 用户态 ELF 或重构后的 CLI
  kpm/
    page_dog.kpm    # 或源码构建产物
  scripts/
    load_kpm.sh
    collect_diag.sh
  install.sh
  pack.sh
```

区别也很重要：你手上的 ZIP 内是按 `vermagic` 分发的传统 `.ko` 风格内核模块包装器，而上面前三个 KPM 项目通常依赖 KernelPatch 的符号解析与 KPM API，理论上不需要为每个 `uname -r` 维护一份 `.ko`。因此重构时更值得参考 `hidhide-module` 的工程组织，而不是保留“几十个内核版本 Shell 自解压 + `insmod`”的分发方式。
